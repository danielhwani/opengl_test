# humanoid_sim

`D:\claude_test\computer_graphics`의 OpenGL 데모(`humanoid_test.c` /
`humanoid_loader_test.c`)가 하던 걷기/트롯 애니메이션을 ROS2
`joint_states` + TF로 재현해서 RViz2로 보기 위한 패키지. 모델 자체는
`gen_humanoid_assets.exe`가 생성하는 `humanoid.urdf` / `quadruped.urdf`
(+ `*_extra.yaml`)를 그대로 쓴다.

**Windows용 ROS2 Humble에서 `colcon build` → `ros2 launch
humanoid_sim display.launch.py`로 실제로 빌드/실행해서 RViz2에
humanoid와 4족 로봇이 둘 다 움직이는 것까지 확인했다.**

### 빌드 중 겪었던 문제: 한글 인코딩

처음 빌드했을 때 `colcon.colcon_core.package_augmentation ERROR
... 'cp949' codec can't decode byte ...`가 났다 - colcon의
`ros_ament_python` 패키지 분석 단계가 `setup.py`를 Windows
한국어 로캘의 기본 코드페이지(cp949)로 읽으려다, 그 안에 있던
UTF-8 한글 설명문을 디코딩하지 못해서 난 에러였다. 빌드는 그
단계를 건너뛰고도 일단 "Finished"로 끝났지만, package.xml 설치나
마커 파일 설치가 암묵적 fallback에 의존하게 돼서 찜찜했다 -
`setup.py`/`package.xml`의 설명문(description)만 영어로 바꿔서
해결했다 (코드 안의 한글 주석은 `.py` 파일을 UTF-8로 그냥 읽으므로
문제없다). 고친 뒤로는 그 에러 없이 깨끗하게 빌드된다.

빌드가 끝난 뒤 `WNDPROC return value cannot be converted to
LRESULT` / `TypeError: WPARAM is simple, so must be an int object
(got NoneType)`가 뜨는 것도 봤는데, 이건 colcon이 빌드 완료 후
**Windows 데스크톱 알림 팝업**을 띄우려다 나는 것으로, 빌드 결과와는
무관한 사소한 문제다 (이미 빌드가 성공적으로 끝난 뒤에 발생).

## 사전 준비

1. `D:\claude_test\computer_graphics`에서 `gen_humanoid_assets.exe`를
   한 번 실행해서 `humanoid.urdf` / `quadruped.urdf` /
   `*_ros.obj` / `humanoid_path.txt` / `quadruped_patrol.txt`가
   그 폴더에 있는지 확인한다 (`humanoid_path.txt`/
   `quadruped_patrol.txt`는 손으로 쓴 파일이라 이미 있을 것이고,
   나머지는 `gen_humanoid_assets.exe`가 만든다).
2. 이 패키지(`humanoid_sim`)를 ROS2 작업공간
   (`D:\claude_test\computer_graphics\ros2_ws`) 아래 `src/`에 둔
   상태 그대로, ROS2 Humble 셸(환경 설정 배치 파일을 소스한 셸)에서:

   ```powershell
   cd D:\claude_test\computer_graphics\ros2_ws
   colcon build --packages-select humanoid_sim
   # (Windows에서 colcon은 보통 call install\setup.bat 로 환경을 적용한다)
   call install\setup.bat
   ```

## 실행

```powershell
ros2 launch humanoid_sim display.launch.py
```

이 런치 파일이 하는 일:

- `robot_state_publisher`를 `/humanoid`, `/quadruped` 네임스페이스로
  각각 띄워서 `humanoid.urdf`/`quadruped.urdf`를 로딩한다 (조인트
  이름이 두 로봇 사이에서 안 섞이게 네임스페이스로 분리했다 - 자세한
  이유는 `launch/display.launch.py`의 docstring 참고).
- `humanoid_state_publisher`/`quadruped_state_publisher`(이 패키지의
  Python 노드)가 걷기/트롯 각도를 `/humanoid/joint_states` /
  `/quadruped/joint_states`로 발행하고, 몸통의 세계 속 위치를
  `world -> base_link` / `world -> quad_base_link` TF로 직접
  발행한다.
- `rviz2`를 띄운다 (저장된 `rviz/humanoid_sim.rviz`를 시도한다).
  실제로 띄워봐서 humanoid와 4족 로봇이 둘 다 RViz2 안에서 걷는
  것까지 확인했다. 혹시 디스플레이가 안 보이면 수동으로 Fixed
  Frame을 `world`로 두고 RobotModel 디스플레이 2개(Description
  Topic을 각각 `/humanoid/robot_description`,
  `/quadruped/robot_description`로)와 TF 디스플레이를 추가하면 된다.

프로젝트 폴더가 `D:\claude_test\computer_graphics`가 아닌 다른
곳이면:

```powershell
ros2 launch humanoid_sim display.launch.py assets_dir:=D:/다른/경로/computer_graphics
```

## 물리 데모: 공을 떨어뜨려 로봇과 충돌시키기 (로봇도 반응함)

`physics_demo.launch.py`는 `display.launch.py`와 똑같이 두 로봇을
띄우고, 거기에 더해 `mujoco_ball_sim` 노드로 MuJoCo 물리 엔진을
돌린다. 공 하나(실제 물리 바디, 자유낙하 + 중력)가 humanoid/4족
로봇의 몸통 충돌 프록시와 실제로 부딪힌다 - **그리고 맞으면 로봇도
반응한다.**

- 처음엔 프록시를 "mocap" 바디(물리 영향은 안 받고 자세만 외부
  TF로 그대로 주입받는)로 만들어서, 공은 튕기는데 로봇은 전혀
  반응이 없었다.
- 그래서 프록시를 질량이 있는 진짜 물리 바디로 바꾸고, 대신 매 틱
  "지금 걷고 있는/순찰 중인 목표 자세"(`humanoid_state_publisher`/
  `quadruped_state_publisher`가 발행하는 `"world"->"base_link_target"`/
  `"world"->"quad_base_link_target"` TF)를 향해 가상의 스프링-댐퍼
  힘/토크를 걸었다. 평소엔 그 목표를 그대로 따라가며 걷지만, 공에
  맞으면 스프링이 늘어나(목표에서 벗어나) 순간적으로 흔들리다가
  다시 걷기 자세로 돌아온다.
- `mujoco_ball_sim`이 그 물리 시뮬레이션 결과(흔들림 포함)를 실제
  `"world"->"base_link"`/`"world"->"quad_base_link"` TF로 발행해서,
  `robot_state_publisher`가 그걸로 전체 로봇 메쉬의 TF를 계산한다 -
  그래서 RViz2에 보이는 로봇 자체가 흔들린다. 두 state publisher는
  `publish_base_link` 파라미터를 `False`로 받아서(이 launch 파일이
  그렇게 띄움) 그 프레임을 직접 발행하지 않는다 - 안 그러면 두
  발행자가 같은 TF 프레임을 두고 충돌한다.

**3초(`RESPAWN_INTERVAL_SEC`)마다 둘 중 한쪽 바로 위에서 공을 다시
떨어뜨린다** - 처음엔 "바닥 아래로 떨어졌을 때만" 다시 떨어뜨리게
해놨는데, 빈 바닥에 착지해서 가만히 멈추면 그 조건을 다시는 만족
못 해 공이 영원히 멈춰버리는 버그가 있었다.

결과는 `/physics_markers`(공 + 반투명 충돌 프록시 2개 - 로봇이
흔들리는 동안 이 프록시도 같이 흔들린다)와 `world -> ball` /
`world -> base_link` / `world -> quad_base_link` TF로 RViz2에
보여준다. 자세한 설계는 `mujoco_ball_sim.py`와
`mujoco/ball_collision.xml`의 docstring/주석 참고.

**실제로 돌려보니, 공에 맞아 쓰러진 뒤로 다시 못 일어나고 바닥에
쓰러진 채로 걷기 목표 쪽으로 계속 끌려가는(기어가는) 문제가
있었다.** 회전 스프링(`SPRING_KP_ROT`, 처음엔 150)이 쓰러진 자세의
중력+바닥 접촉 마찰을 이기고 다시 세울 만큼 세지 않아서였다 -
위치 스프링(강함)만 이기고 로봇을 계속 끌고 다닌 것. 쓰러진 뒤
스스로 균형을 잡고 일어서는 건 실제 다리로 버티는 제어가 필요한
훨씬 어려운 문제라, 그 상황 자체를 피하는 쪽으로 고쳤다 -
`SPRING_KP_ROT`을 4000까지 크게 올려서(그리고 감쇠도 `SPRING_KP_POS`
처럼 관성 기준 임계댐핑으로 자동 계산하도록 바꿔서), 웬만한 충격
으로는 애초에 안 쓰러지고 "잠깐 휘청였다가 바로 돌아오는" 정도로만
보이게 했다.

**그래도 스프링 상수는 완전히 튜닝된 게 아니다.** `SPRING_KP_POS`/
`SPRING_KP_ROT`의 감쇠(kd)는 각각 질량/관성으로 임계댐핑을 계산해서
자동으로 맞추지만, 비례 계수(kp) 자체와 공/로봇 질량, "얼마나 세게
흔들렸으면 좋겠는지"는 실제로 보면서 조절해야 하는 값이다.

**박스 프록시가 로봇 발밑(땅)에 생기는 버그도 있었다.** 스프링
목표로 쓰는 `base_link_target`/`quad_base_link_target`은 발 높이
(z=0) 기준인데, 충돌 박스는 몸통(torso) 크기라 그 사이 높이
차이(URDF의 `base_to_body`류 fixed 관절 오프셋, humanoid 1.9m /
quad 0.75m)를 안 더해줘서 생겼다 - `HUMANOID_BODY_HEIGHT_OFFSET`/
`QUAD_BODY_HEIGHT_OFFSET`을 목표 위치에 더하고, 반대로
"world"->"base_link"를 발행할 때는(robot_state_publisher가 그
오프셋을 URDF에서 또 적용하므로) 그 오프셋을 몸통의 현재 방향으로
회전시켜 다시 빼주도록 고쳤다(`body_pose_to_root()`).

**회전 스프링을 세게 올리자(쓰러짐 방지), 이번엔 로봇이 통째로
날아가 버리는 더 심한 버그가 생겼다.** ROS2/RViz2 GUI 없이도
`ros2 run`으로 노드를 직접 띄우고 `ros2 run tf2_ros tf2_echo`로 TF
값을 숫자로 찍어보면서(+ MuJoCo를 독립적으로 돌리는 진단 스크립트)
원인을 찾았다:
- quad_proxy가 방향을 틀기 시작하는 순간부터 각속도(`|w|`)가 몇
  틱 안에 기하급수적으로 폭주했다(0 -> 27 -> 180 -> 103920 ...).
  길쭉한 상자라 축마다 관성이 꽤 다른데(intermediate axis 문제),
  댐핑을 평균 관성 하나로만 계산하는 선형 PD 제어가 그 자이로스코픽
  결합을 못 잡아낸 것으로 보인다.
- `MAX_FORCE`/`MAX_TORQUE`로 우리가 거는 힘/토크를 제한해도 안
  잡혔다 - 그 결과로 생긴 빠른 회전이 MuJoCo의 접촉(contact) 솔버
  에서 "터널링"(한 스텝 사이 과도한 침투 -> 비현실적으로 큰 충돌
  임펄스)을 일으켜, 우리가 안 건 속도까지 치솟았다(최대 9백만
  rad/s 관측).
- 결국 물리 스텝 "이후"(매 substep마다)에 선속도/각속도 자체를
  `MAX_LIN_VEL`/`MAX_ANG_VEL`(15 m/s, 15 rad/s)로 직접 눌러주는
  방식으로 해결했다 - 걷거나 순찰하는 로봇이 이보다 빨리 움직일
  이유가 없으니 안전한 상한이다. 25초짜리 헤드리스 테스트로 더 이상
  폭주하지 않음을 확인했다(위치가 한 번도 합리적 범위를 벗어나지
  않았다).
- 다만 완전히 매끄럽진 않다 - 클램프가 걸리는 동안은 로봇이 다소
  휘청인다(RPY로 수십 도 정도 기울었다가 가라앉는 모습을 TF로
  확인함). RViz2로 실제로 보면서 더 다듬어야 한다.

**중요 - MuJoCo는 rosdep으로 안 받아진다.** `mujoco_ball_sim`은 pip
패키지 `mujoco`가 필요하다. 처음엔 conda 환경(`mujoco_ros_38`)에
설치하면 될 줄 알았는데, 이 ROS2 Humble(Windows) 설치는 colcon/ros2
전체가 **항상 `C:\Python38`을 쓰도록 고정**돼 있었다 -
`conda activate`를 해도 `colcon` 명령 자체가 그 conda 환경에
설치돼 있지 않으면(`colcon-common-extensions`를 거기 따로 깐 적이
없으면) PATH에서 결국 `C:\Python38`의 `colcon.exe`가 호출되기
때문이다. 그래서 `mujoco`를 그 Python에 직접 설치해야 했다:

```powershell
C:\Python38\python.exe -m pip install mujoco
```

(PyPI 인증서 문제 - `NO_CERTIFICATE_OR_CRL_FOUND` 류 SSL 에러가
나면, `--trusted-host pypi.org --trusted-host files.pythonhosted.org`
를 덧붙이면 우회된다. 이 환경에서 실제로 이 방법으로 설치됐다.)


## 반응형 물리 튜닝 (진행 중)

위 "날아가는 버그"를 고친 뒤에도, 실제로 공을 맞혀보면서 계속
문제가 나왔고 하나씩 고쳤다 - 순서대로:

1. **공이 로봇 발밑(땅)에 박스로 나타남** - 이미 위에 적은
   `HUMANOID_BODY_HEIGHT_OFFSET`/`body_pose_to_root()` 버그.
2. **공을 맞아도 거의 반응이 없거나(과댐핑) 반대로 계속 떨림
   (언더댐핑)을 왔다갔다** - `MAX_ANG_VEL`을 15→6으로 낮추고, 각속도
   제곱에 비례하는 추가 감쇠(`ROT_QUAD_DRAG`, 공기저항 느낌 - 빠르게
   돌 때만 세게 제동)를 추가했다. 그래도 damping multiplier 하나로
   둘 다 만족시키기 어려워서 계속 왔다갔다했다.
3. **4족 로봇이 공과 무관하게 계속 흔들림** - 알고 보니 patrol
   방향 전환(최대 ±90도)이 원래 꽤 급한데, 회전 스프링이 그 "정상
   애니메이션 목표"조차 못 따라가서 생긴 지연(lag)-흔들림이었다
   (공 충돌 반응 문제가 아니었음).
4. **결국 humanoid/quad의 회전 스프링을 완전히 분리**했다 -
   `HUMANOID_KP_ROT=800`(경로가 완만해서 안 뻣뻣해도 됨) +
   `HUMANOID_ROT_DAMPING_MULTIPLIER=1.8`, `QUAD_KP_ROT=1500`(급선회를
   따라가려면 더 뻣뻣해야 함) + `QUAD_ROT_DAMPING_MULTIPLIER=1.3`.
5. **공이 둘 중 아무 로봇에나 무작위(50:50)로 떨어져서, 운이 나쁘면
   한쪽이 한동안 안 맞아 "반응이 없어졌다"는 느낌을 줄 수 있었다** -
   `respawn_ball()`을 번갈아(humanoid, quad, humanoid, ...) 가게
   바꿨다(`next_respawn_is_humanoid`).
6. **target_vel 계산에서 에일리어싱 버그 발견 및 수정** -
   `humanoid_state_publisher`/`quadruped_state_publisher`는 50Hz로
   TF를 발행하는데 `mujoco_ball_sim`은 100Hz로 읽어서, 고정된 틱
   주기(`TIMER_PERIOD_SEC`)로 나누면 한 틱은 "값이 안 변함"(속도
   0으로 계산됨), 다음 틱은 그 두 배로 튀는 문제가 있었다 -
   `lookup_target()`이 TF 메시지 자체의 타임스탬프를 같이 돌려주고,
   `update_proxy()`가 그 실제 시간 차이로 속도를 계산하도록 고쳤다
   (같은 타임스탬프를 또 읽은 틱은 이전 속도를 그대로 재사용).

**아직 안 풀린 문제 (업데이트, 다음 세션)**: 6번을 고친 뒤에도
"휴머노이드가 공을 맞기 전부터(처음부터) 계속 흔들린다"는 보고가
계속됐다. `ros2 bag record -o <name> /tf /tf_static`로 실제 TF를
파일로 녹화해서(네트워크/DDS에 전혀 안 끼어들고 `rclpy.serialization.
deserialize_message`로 sqlite3 `.db3` 파일을 오프라인으로 직접
파싱 - 이 방법이 이 환경에서 가장 안전하게 데이터를 확인하는 방법
이었다) 분석해보니:

- **회전(yaw)과 높이(z)는 정상**이다 - 쓰러지거나 팽이처럼 돌지
  않는다.
- **수평 위치(x,y)가 첫 공 충돌 시점부터 녹화가 끝날 때까지
  (10초 이상) 초속 7~19m/s급으로 계속 진동하며 거의 안 가라앉는다.**
  공이 로봇에서 8m 이상 떨어져 있을 때도 똑같이 계속돼서, 공이
  계속 때려서 그런 게 아니라 **스프링 피드백 자체가 자기유지하는
  리밋 사이클(limit cycle)**로 보인다.
- 이번 세션 내내 **회전** 스프링만 과댐핑/쿼드래틱 드래그로 손봤고
  **위치** 스프링(`SPRING_KP_POS`)은 맨 처음 값(순수 임계댐핑)
  그대로였다 - 위치에도 똑같이 과댐핑(`POS_DAMPING_MULTIPLIER=1.8`)
  + 속도 제곱 감쇠(`POS_QUAD_DRAG=20`)를 추가하고, 그 감쇠력이
  깎이지 않도록 `MAX_FORCE`도 5000→20000으로 올렸다 - **그런데도
  거의 효과가 없었다** (여전히 같은 패턴).
- 마지막으로, 근본 원인을 더 파기보다 "속도가 `MAX_LIN_VEL`/
  `MAX_ANG_VEL`의 90% 이상으로 0.5초 넘게 계속 붙어있으면 그냥
  목표 자세로 강제 스냅시키는" 안전장치(`check_stuck_and_recover()`)
  를 추가했다 - 처음 3초(공 맞기 전)는 확실히 조용해졌지만, 맞은
  뒤로는 속도가 7~19m/s 사이를 오르내리며 **여전히 깨끗하게
  원래 상태로 안 돌아온다.**

세 번의 서로 다른 처방(위치 과댐핑, 힘 제한 상향, 강제 스냅
안전장치)이 다 부분적으로만 효과가 있어서, **"가상 스프링을
`xfrc_applied`로 직접 미는" 지금 설계 자체의 구조적 한계**일 가능성이
있다고 보고 이번 세션은 여기서 마무리했다. 다음에 이어서 볼
방향: (a) MuJoCo 네이티브 조인트 기반 액추에이터/`equality`
제약으로 바꿔서 암묵적(implicit) 적분의 이득을 위치에도 받게
하거나, (b) 왜 댐핑을 올려도 안 죽는지(에너지가 정확히 어디서
재생산되는지) 더 깊이 분석하거나, (c) 지금 수준에서 받아들이고
다른 작업으로 넘어가는 것 중 선택.

### 해결 (2026-11-16): 네이티브 `mocap`+`weld` 제약으로 재설계 - 리밋 사이클 사라짐

4족 보행에 네이티브 `<position>` 액추에이터를 쓰고 나서(위 "4족
로봇 실제 관절 구동 보행" 섹션) 그게 `xfrc_applied` 방식보다
훨씬 안정적이라는 게 분명해졌다 - "직접 만들기 전에 라이브러리
기본 기능부터 찾아보자"는 교훈을 공 데모에도 적용했다.

**방법**: `ball_collision.xml`에 `mocap="true"` 바디 2개
(`humanoid_target`/`quad_target`, 물리 영향 없음, 자세만 외부에서
직접 주입)를 추가하고, `<equality><weld>`로 `humanoid_proxy`/
`quad_proxy`를 각자의 mocap 목표에 "용접"했다. `mujoco_ball_sim.py`
는 이제 매 틱 `data.mocap_pos`/`data.mocap_quat`에 TF로 받은 목표
자세를 그대로 써넣기만 하면 된다 - `apply_spring()`/
`apply_rotation_spring()`/`check_stuck_and_recover()`와 그 주변의
모든 상수(`SPRING_KP_POS`, `HUMANOID_KP_ROT`/`QUAD_KP_ROT`,
`MAX_FORCE`/`MAX_TORQUE`, `*_DRAG`, `*_DAMPING_MULTIPLIER`,
`STUCK_*`)가 전부 필요 없어져서 삭제했다(과거 버전은 git
히스토리에 남아있음). `target_vel`을 TF 타임스탬프로 계산하던
에일리어싱 보정 코드도 통째로 사라졌다 - mocap은 속도가 없는 순수
kinematic 위치/방향이라 그 자체로 아예 필요 없는 문제였다.

**검증**: ROS 없이 순수 MuJoCo 스크립트로 - (1) 별도 프로토타입
장면에서 solref 시간상수를 0.02~2.0까지 쓸어보며 다양한 세기로
공을 쐈고, (2) 실제 `ball_collision.xml`로 공을 `humanoid_proxy`
위에서 떨어뜨려봤다. **두 경우 모두 단 한 번도 리밋 사이클이나
발산이 재현되지 않았다** - 맞을 때마다 매번 깨끗하게 감쇠해서
멈췄다(이전엔 16~20m/s대로 영원히 안 가라앉았던 바로 그 패턴).
접촉(contact)과 weld 제약이 같은 솔버 스텝에서 함께 풀리는 게
`xfrc_applied`(명시적 힘, 접촉과 따로 풀림)보다 근본적으로 더
안정적인 것으로 보인다.

**현재 반응 크기는 다소 작다** - solref 시간상수 0.15로 잡은 상태로,
20m/s급 충격에도 변위가 수 mm~수 cm 수준이다(너무 뻣뻣해서 안
그런지, 실제 데모에서 직접 보면서 시간상수를 키워 더 눈에 띄게
조정할 수 있다 - 값을 올릴수록 더 크게/느리게 흔들린다). 회전
방향(humanoid 경로 완만 vs quad 급선회)에 따라 kp/damping을 따로
튜닝해야 했던 것도 이제 필요 없다 - weld 하나가 위치+회전을 한
제약으로 같이 처리해서 humanoid/quad를 분리할 이유가 없어졌다(둘
다 같은 `solref="0.15 1"` 공유).

### 추가 업데이트 (2026-11-16): 물리 데모 라이브 테스트에서 발견된 버그 3개

실제로 `physics_demo.launch.py`를 띄워보고 나서 발견/수정한 것들.

**1) 4족 로봇 다리가 무릎 아래로 안 보임 ("날아다니는 것처럼" 보임)**:
`quadruped_state_publisher.py`(이 데모의 순찰/트롯 애니메이션 담당)가
무릎 관절(`QuadLegFL_to_QuadShinFL` 등 4개, 다른 세션에서 이미 URDF에
추가됨)을 `/joint_states`에 전혀 발행하지 않고 있었다 - 한 번도 값을
못 받은 관절은 robot_state_publisher가 그 아래 링크(정강이)의 TF를
아예 계산 못 해서 렌더링이 안 된다. 트롯 위상에 맞춰 무릎도 같이
굽혔다 펴지는 공식(`KNEE_SWING_AMP_DEG * max(0, -cos(phase))`,
`quad_mujoco_walk.py`와 같은 패턴)을 추가해서 고쳤다.

**2) 다리를 고치고 나니 몸통 전체가 땅 위로 약간 떠 있음**: 원인은
`gen_humanoid_assets.c`가 4족 로봇의 엉덩이 관절을 `QuadBody`
메쉬의 "중심"(상자 원점)에 매달고 있었던 것 - humanoid 쪽
(`body_to_leftleg`/`rightleg`)은 `leg_z = -BODY_H/2`(몸통 "바닥")를
쓰는데 4족 로봇 쪽만 리터럴 `0`이 박혀 있었다. `base_to_quadbody_z
= QUAD_LEG_LEN + QUAD_BODY_H/2` 공식 자체는 "엉덩이가 몸통 바닥에
있다"고 가정하고 있어서, 실제로는 몸통 높이의 절반(`QUAD_BODY_H/2
= 0.2m`)만큼 어긋나 있었다 - URDF(`write_quadruped_urdf`)와 OpenGL
씬 파일(`write_scene`) 양쪽 다 같은 버그였다. 양쪽 다
`-QUAD_BODY_H/2`로 고치고 `gen_humanoid_assets.exe`를 재생성했다.
(이 버그는 무릎을 추가하기 전부터 있었던 것으로 보이는데, 그때는
다리 전체가 안 보여서 "발이 땅에 닿는지" 눈으로 확인할 기준점이
없어 아무도 눈치 못 챘던 것 같다.)

  컴파일러 관련 삽질: `gen_humanoid_assets.c`를 MinGW gcc로 재컴파일할
  때 `gcc.exe`는 실행되는데(`--version` 정상) 실제 컴파일/링크
  단계(`cc1.exe` 실행)에서 매번 아무 메시지 없이 exit code 1로
  죽었다 - `cc1.exe`를 직접 호출해보니 Windows 에러 코드
  `0xC0000135`(DLL_NOT_FOUND)였다. 원인은 PATH에
  `ucrt64/bin`이 없어서 `cc1.exe`가 자기 런타임 DLL을 못 찾은
  것(`gcc.exe` 자신은 같은 폴더에 있어서 괜찮았지만, `cc1.exe`는
  `lib/gcc/...` 하위 폴더에 있어서 PATH가 필요했다) - PATH에
  `ucrt64/bin`을 추가하고 나서야 정상적으로 컴파일됐다.

**3) weld 재설계 후 "공에 맞으나 안 맞으나 똑같이 안정적"으로
보임**: 리밋 사이클은 확실히 없어졌지만, 실제로는 프록시가
weld로 목표를 따라가면서도 **자기 무게 때문에 항상 거의 동일한
양만큼 처져 있었다** - 독립 스크립트로 확인하니 처짐 크기가 공
타격 여부/위치와 무관하게 거의 일정했고(solref 시간상수에
비례해서 커짐: 0.15->1.1cm, 0.3->4.6cm, 0.5->12.5cm), 진짜 "공에
맞아서 생기는" 반응은 그 안에 묻혀서 거의 안 보였다. mocap
애니메이션이 이미 "서 있는" 자세를 책임지므로 프록시가 중력에
또 처질 필요는 없다는 뜻 - `humanoid_proxy`/`quad_proxy`에
`gravcomp="1"`을 줘서 이 처짐 자체를 없앴다. (삽질: MuJoCo python
모델 객체에 런타임으로 `model.body_gravcomp` 배열만 바꿔서는 전혀
효과가 없었다 - XML 속성(`gravcomp="1"`)으로 컴파일 시점에 줘야
적용됐다.) 처짐을 없애고 나니 이번엔 순수 충돌 반응 자체가 너무
작았다(공 0.5kg·2m 자유낙하 운동량이 15kg 프록시엔 mm 단위) - 공
질량을 3kg로, weld `solref`을 0.15->0.5로 올려서 맞을 때마다
1~2cm 보이게 흔들리고 다음 낙하(3초) 전에 항상 수 mm 이내로
복귀하는 걸 독립 스크립트로 20번 연속 무작위 낙하시켜 확인했다
(누적 드리프트 없음).

### 추가 업데이트: 10초 검증의 함정 - 장시간 드리프트로 결국 뒤집힘

사용자가 `view_quad_walk.py`로 1분 넘게 지켜보더니 "가장자리에 가서
뒤집어지네?"라고 확인 - 위에서 찾은 1.1Hz를 180초까지 돌려보니,
**18~20초쯤 롤(좌우 기울기)이 서서히 커지다가 반드시 뒤집혀서
옆으로 누운 채 멈췄다.** 한 번의 사고가 아니라 **누적되는 드리프트**
였다(0~18초: 기울기가 4.5도→9.9도로 서서히 증가, 18~20초: 급격히
108~117도로 뒤집힘, 그 뒤: 90도로 누운 채 안정). 10초짜리 검증
으로는 절대 안 보이는 문제였다.

0.5Hz 간격으로 0.8~1.2Hz를 180초까지 다시 쓸어봤다:

| 주파수 | 180초 결과 |
|---|---|
| 0.8~0.95Hz | 전부 안정(기울기 5~6도대), 안 넘어짐 |
| 1.0Hz | 안정은 한데 60초 만에 옆으로 8.5m나 쏠림 |
| 1.1Hz | **18~20초쯤 반드시 뒤집힘** |
| 1.2Hz | 더 빨리 넘어짐 |

0.8~0.95Hz 중에서는 **0.85Hz**가 옆으로 쏠리는 양(lateral drift)이
가장 작아서(180초에 1.8m, 0.95Hz는 120초에 17.8m나 쏠림) 가장
똑바로 걷는다 - 최종적으로 `GAIT_FREQ_HZ`를 1.1 → 0.85로 바꿨다.

**교훈**: 걸음걸이/제어 게인을 검증할 땐 짧은 구간(10초)만 보고
"됐다"고 판단하면 안 된다 - 리밋 사이클이나 서서히 쌓이는 드리프트
같은 문제는 보통 한참 지나야 드러난다. 최소 1~2분은 돌려봐야
안다. (조명도 이때 같이 손봤다 - `<headlight>`로 전역 밝기를
더하고 `light`를 `directional`로 바꿔서, 로봇이 원래 조명의
원뿔/도달 범위를 벗어나도 가장자리가 어두워지지 않게 했다. 그 뒤
"전역 조명이 너무 밝아서 스폿라이트가 안 보인다"는 피드백으로
`headlight`/`light`의 ambient/diffuse를 다시 낮췄다.)

### 추가 업데이트: 속도 개선 (보폭 32도)

0.85Hz로는 "너무 느려서 답답하다"는 피드백을 받았다. 주파수를
다시 올리면 장시간 불안정(위 섹션)이 재발할 수 있어서, 대신 **보폭
(엉덩이 스윙 진폭)**을 0.85Hz로 고정한 채 150~300초씩 쓸어서
찾았다:

- 30→35도까지는 빨라지다가(35도: 150초에 29.8m), 35도부터 롤
  최대값이 눈에 띄게 커지기 시작(7.7도) - 안전 마진을 더 보려고
  32~37도 구간을 240초로 다시 쓸어봤다.
- 32~37도는 전부 안 넘어지긴 했지만(최대 롤 5.9~9.8도), **옆으로
  쏠리는 양이 값마다 들쭉날쭉했다**(32도: 0.7m, 34도: 18.9m, 36도:
  27.6m - 매끄러운 경향이 아니라 민감한/카오스적인 구간으로
  보인다).
- **32도**가 전진(240초에 38.6m)도 빠르고 옆쏠림도 제일 적어서
  (0.7m) 채택했다. 300초(5분)까지 다시 확인해도 48m 전진, 옆쏠림
  1.6m, 최대 롤 5.9도로 안정적이었다.

`SWING_AMPLITUDE_DEG`를 30 → 32로 바꿨다. 체감 속도가 확실히
빨라졌을 것이다(기존 대비 300초 기준 약 20~25% 더 빠름).

### 추가 업데이트 (2026-11-16): `/cmd_vel`로 방향 조정

RViz2에서 걷는 것까지 확인한 뒤, `geometry_msgs/Twist`를 받는
`/cmd_vel` 토픽으로 전진 속도(`linear.x`)와 회전 속도(`angular.z`)를
teleop처럼 조정할 수 있게 했다. 이번에도 실제 로봇/ROS 없이 순수
MuJoCo 스크립트로 먼저 검증했다.

**회전을 만드는 방법**: 엉덩이에 요(yaw)/벌림 관절이 없어서(피치
1축뿐) 좌우로 다리를 "벌려서" 도는 건 불가능하다 - 대신 트롯
걸음걸이에서 **왼쪽 다리(FL,BL)와 오른쪽 다리(FR,BR)의 보폭(진폭)을
다르게** 줘서 돌게 했다(오른쪽이 더 크게 걸으면 왼쪽으로 돈다).

**검증 중 발견한 함정 - 이 매핑은 선형이 아니라 꽤 예민하다**:
- 기존 직진 최대 보폭(32도)에 고정한 채 좌우 보폭 차이를 0~12도까지
  60초씩 쓸어봤더니, 회전량이 차이값에 단순히 비례하지 않았다
  (3도: +52.6도 회전, 6도: **그냥 넘어짐**, 9도: -73.9도로 반대
  방향 회전!). 차이값을 0.5도 단위로 세밀하게 다시 쓸어보니 **0~3도
  구간만 안전하고 깨끗하게(회전량이 거의 선형으로 비례, 안 넘어짐)
  동작**했고, 4.5도부터 회전력을 잃기 시작해 6도부터는 넘어졌다.
- 그런데 **기본 직진 보폭을 32도(최근에 속도 때문에 올린 값) 그대로
  두고 거기에 회전 차이 3도를 더했더니, 90초 검증에서 오히려
  뒤로(-1.4m) 갔다** - 32도 보폭 자체가 이미 "민감한 구간"에
  가까워서(위 속도 개선 섹션 참고) 회전을 더하면 쉽게 카오스적으로
  틀어지는 것으로 보인다. 보폭을 25도로 낮춘 상태에서는 같은 회전
  차이(3도)가 90초 동안 75.2도 회전(일관된 방향, 안 넘어짐)으로
  깨끗하게 동작했다.
- 그래서 **회전량이 커질수록 전진 보폭을 32도(회전 없음)에서
  25도(최대 회전) 쪽으로 같이 낮추는 보정**을 넣었다(선형 보간).
  이 조합의 중간값(28.5도 보폭 + 1.5도 차이)도 90초 검증으로
  확인했고, 마지막으로 "정지(10s)->전진 가속(20s)->전진+좌회전
  (40s)->직진(30s)->전진+우회전(40s)->정지(10s)" 순서의 150초짜리
  실제 teleop 시나리오로 전체 매핑을 통과시켜서 최종 확인했다
  (최대 롤 5.7도, 안 넘어짐).

**결과물 - 느리다**: 엉덩이가 피치 1축뿐이라 회전 자체가 기계적으로
약해서, 최대 설정(각도 차이 3도)으로도 초당 약 0.8~0.9도밖에 못
돈다 (`CMD_MAX_TURN_RATE_RAD_S = 0.015` rad/s). 급커브는 안 되고
서서히 방향을 트는 정도다. **더 빠른 회전이 필요해지면, 무릎을
추가했던 것과 같은 패턴으로 엉덩이에 두 번째(요) 관절을 추가하는
게 다음 단계**일 것이다 - 지금은 기계적 한계로 남겨둔다.

**적용된 파일**:
- `humanoid_sim/quad_mujoco_walk.py`: `/cmd_vel` 구독 추가

### 회전을 더 빠르게 하려다 포기한 시도 두 가지

사용자가 "회전이 너무 느린데"라고 확인 - 더 빠르게 만들려고 두 가지를
시도했는데, 둘 다 README 분량을 아끼기 위해 결론만 적는다(자세한
수치는 `quad_mujoco_walk.py`의 `compute_leg_targets()`와
`project_computer_graphics_status.md` 메모리 참고):

1. **좌우 보폭 차이를 3도보다 더 키우기**: 회전량이 차이값에 비례하지
   않고 카오스적이었다(60초 기준 3도→+52.6도, 6도→넘어짐, 9도→
   -73.9도로 방향이 반대로 뒤집힘). "한쪽 다리를 반대로 걷게 하는"
   탱크 피벗 방식도 시도했지만 마찬가지로 비선형적(피벗 강도
   0.8에서 3배 빨라지다가 1.0(완전 대칭)에서는 회전이 0이 되고
   오히려 뒤로 감)이었다 - 균형 피드백이 없는 열린 루프 걸음걸이라
   회전을 세게 넣을수록 예측 불가능해지는 게 근본 한계로 보인다.
2. **엉덩이에 요(yaw)/벌림 관절 추가** (무릎 추가와 같은 기계적
   해결 패턴, 사용자가 선택): 독립 MJCF 프로토타입으로만 검증(실제
   프로젝트 파일은 안 건드림) - 회전 명령이 전혀 없이 그냥 직진만
   시켜도, 요 액추에이터 게인을 5~2000까지 바꿔봐도 2~3초 안에
   불안정해졌다. 원인으로 추정되는 것: 원래 1축(피치) 엉덩이는
   스탠스 중 발-바닥 마찰이 만드는 비틀림 토크를 전부 몸통(관성
   커서 거의 안 흔들림)으로 떠넘겼는데, 요 관절을 추가하면 그
   토크가 질량이 작은 다리 자체(허벅지+종아리 0.3kg)를 그 축으로
   제멋대로 돌려버리는 길이 새로 생긴다 - 발은 마찰로 고정된 채
   다리 위쪽만 홱홱 도는 셈이라 PD 게인 조정만으로는 못 잡는
   구조적 문제다. 제대로 고치려면 "스탠스 중엔 요 관절을 꽉 잠그고
   스윙 중에만 풀어주는" 위상 의존적 제어가 필요해 보이는데, 꽤 큰
   엔지니어링이라 보류했다.

**결론: 지금의 느린(초당 0.8~0.9도) 좌우 보폭 차이 방식을 최종으로
유지한다.**

### 추가 업데이트: 후진

cmd_linear_x가 음수면 후진한다.

**먼저 전진이 되는 원리.** 엉덩이 각도는 `A·sin(phase)`로 앞뒤로
흔들리고, 무릎은 `max(0, -cos(phase+offset))`로 한쪽 반주기에만
굽혀진다. 한 주기를 반으로 나누면:
- **스탠스(무릎=0, 쭉 뻗음)**: 엉덩이가 뒤→앞으로 증가하는 동안 -
  발은 마찰로 땅에 박혀있으니, 다리가 막대(지지대)처럼 엉덩이를
  축으로 회전하면서 **몸통을 앞으로 밀어낸다.**
- **스윙(무릎=굽음)**: 엉덩이가 앞→뒤로 돌아가는 동안 - 발이 땅에서
  떨어져 있으니 다리를 들어서 다음 스텝 위치로 복귀만 한다(바닥에
  힘을 안 줌).

즉 "스탠스=뻗은 다리로 밀기"와 "스윙=굽힌 다리로 복귀"가 서로 맞는
타이밍이어야 추진력이 나온다.

**단순히 엉덩이 부호만 뒤집으면 왜 안 되나.** 엉덩이가 증가/감소하는
구간은 뒤집히는데 무릎이 "언제 굽을지" 타이밍은 그대로라서, 이제는
엉덩이가 밀어야 할 구간(증가)에 하필 무릎이 굽어있는 스윙 타이밍이
겹쳐버린다 - 발이 땅에 안 눌린 채로 "밀려는 동작"만 하니 추진력이
상쇄돼서 거의 제자리걸음만 났다(90초에 -0.37m, 독립 스크립트로
검증).

**무릎 타이밍도 같이 옮겨야 하는데, 정확한 각도는 수식으로 바로 안
나왔다.** 직관적으로는 "반주기(180도)만큼 밀어서 스탠스/스윙을
통째로 바꿔치기"하면 될 것 같았지만, 실제로 해보니(수식상 180도
이동 = 무릎 공식의 코사인 부호를 반전시키는 것과 완전히 같음)
오히려 다시 **전진**이 나왔다(+14~16m류, 거의 그대로) - 무릎
공식에 `max(0, ...)` 클리핑이 있어서 사인파처럼 "반주기 밀면
완전히 반대"가 되는 깔끔한 대칭이 아니기 때문이다. 그래서
-90/-60/-30/30/60/90/120/150도를 직접 쓸어본 결과(60초씩), **+90도**
위상 이동이 확실한 후진을 냈다(60초에 -14.2m) - 즉 엉덩이는 부호
반전, 무릎 위상엔 180도가 아니라 **진짜 90도만큼의 이동**을 추가로
더해야 한다. 180초로 재검증해도 -43.5m(전진과 비슷한 크기), 기울기
5도대로 안정적이었다. **이 +90도는 유도가 아니라 쓸어서 찾은
값이다** - 회전 때도 그랬듯, 이 다리-접촉 시스템은 손으로 깨끗하게
유도하는 것보다 직접 쓸어보는 쪽이 더 믿을만하다는 패턴이 여기서도
반복됐다.

후진 중에는 회전(angular.z)을 무시한다 - 후진+회전 조합은 아직
검증 안 했다. 전진→정지→후진→정지 전환도 50초 시나리오로 확인했고,
전환 순간 충격 없이 매끄러웠다.

## 진짜 물리 4족 로봇에 공 던지기 (`quad_physics_walk_ball.launch.py`)

`mujoco_ball_sim.py`의 공 데모는 mocap+weld로 "항상 제자리로 끌어
당기는" 장치가 있어서 아무리 세게 맞아도 결국 복귀한다 - 사용자
표현으로 "약간 꼼수"다. 그럼 꼼수 없이 **진짜 관절 액추에이터로
걷는** `quad_mujoco_walk.py`/`quad_walk.xml`에 공을 던지면 어떻게
될지 궁금해서 만들었다.

**먼저 ROS 없이 확인(독립 스크립트)**: 로봇 바로 옆(0.7m)에서 공을
던져(비행 중 중력으로 처져서 빗나가지 않게 속도에 맞춰 약간의
수직 보정을 줌) 실제 접촉이 일어나는지(`data.ncon`으로 확인)까지
검증했다. 결과:
- 0.5kg/2m/s: 거의 못 느낌, 계속 걸어감
- 0.43kg(축구공)/5m/s: 맞는 순간 기울기가 18도/피치 16도까지
  튀었다가 **1초 만에 스스로 원래 걸음 수준(3~4도)으로 회복** -
  균형 피드백 컨트롤러가 전혀 없는데도(다리는 그냥 정해진 각도
  패턴을 쫓아갈 뿐) 걸음이 계속되면서 우연히 다시 균형을 잡았다.
- 2.0kg/6m/s: **그대로 쓰러짐**(0.9초 만에 roll이 180도까지 돌아가
  옆으로 누움) - 쓰러진 뒤엔 "일어나기" 동작이 없어서 다리만 허공에서
  계속 트롯 패턴을 반복할 뿐 못 일어난다.
- 3.0kg/10m/s: 더 빨리(0.5초) 쓰러짐.

mocap+weld 데모와 달리 **"맞으면 항상 복귀"가 전혀 보장되지 않는다**
- 이게 진짜 물리와 트릭의 핵심 차이다.

**MuJoCo 자체 뷰어로도 확인 가능** (ROS 없이, `mujoco/
view_quad_walk_ball_throw.py`): `view_quad_walk.py`와 같은 화살표 키
걷기 조작 + `/`(슬래시) 키를 누를 때마다 위 세기 목록을 순서대로
하나씩 던진다. 처음엔 Space로 하려 했는데, Space가 MuJoCo 뷰어
자체의 일시정지 토글과 겹쳐서(커스텀 `key_callback`은 *추가로만*
전달되고 뷰어 자체 바인딩을 못 막음 - 화살표 키를 쓰는 것과 같은
이유) 누를 때마다 재생/정지도 같이 토글돼버려 `/`로 바꿨다.

**ROS2/RViz2 버전**: `quad_mujoco_walk_ball.py` + `quad_physics_walk_
ball.launch.py`. `quad_mujoco_walk.py`의 `compute_leg_targets()`/
상수를 그대로 import해서 재사용하고(걸음걸이 공식을 또 베끼지
않음), `quad_walk.xml` 파일 자체는 안 건드리고(다른 데모가 그대로
쓰므로) 내용을 읽어서 공 바디를 메모리상에서만 끼워 넣어 컴파일한다
(뷰어 버전과 동일 기법). 공은 URDF가 없으므로 `mujoco_ball_sim.py`와
같은 방식(MarkerArray, 빨간 구)으로 `physics_markers` 토픽에
발행한다 - 토픽 이름을 똑같이 맞춰서 기존 `rviz/humanoid_sim.rviz`의
PhysicsMarkers 디스플레이를 그대로 재사용했다(새 rviz 설정 불필요).

실행:
```
ros2 launch humanoid_sim quad_physics_walk_ball.launch.py
```
다른 터미널에서 공 던지기(약→강 순서로 순환) - **서비스 호출**이라
던진 공의 질량/속도가 호출한 바로 그 터미널에 응답으로 찍힌다:
```
ros2 service call /quadruped/throw_ball std_srvs/srv/Trigger "{}"
```
걷게 하려면(기존 `quad_physics_walk.launch.py`와 동일):
```
ros2 topic pub /quadruped/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.16}, angular: {z: 0.0}}" -r 10
```
또는 매번 `ros2 topic pub`을 치기 귀찮으면 아래 `teleop_keyboard` 노드를 쓸 것.

**투척 정보 표시**: 처음엔 터미널 로그(`get_logger().info()`)로만
질량/속도를 보여줬는데, 사용자가 "RViz 보는 중엔 안 보인다"고
확인 - 공 바로 위에 `TEXT_VIEW_FACING` 마커(항상 카메라를 보는
텍스트)로 `0.43kg / 5m/s`처럼 직접 표시하게 바꿨다(`physics_markers`
토픽에 구 마커와 같이 발행).

**launch 터미널에 로그가 안 찍히는 문제 -> 토픽에서 서비스로 전환**:
텍스트 마커는 바로 보이는데도 `ros2 launch`를 띄운 터미널엔 "투척:
질량=..." 로그가 전혀 안 나타난 적이 있었다 - 콜백은 분명 정상
실행 중인데(마커가 매번 갱신됨) 로그만 안 보였다. 원인은 Windows
에서 `ros2 launch`가 자식 프로세스의 표준출력을 파이프로 받는데
(진짜 터미널이 아님), 그러면 C 표준입출력 라이브러리가 자동으로
라인 버퍼링 대신 풀(블록) 버퍼링으로 전환돼서 - 로그가 바로 안
나오고 쌓였다가 버퍼가 차거나 프로세스가 끝날 때야(종료 시 flush)
한꺼번에 나온다. `Node()`에 `emulate_tty=True` +
`additional_env={"PYTHONUNBUFFERED": "1"}`을 줘봤지만(Windows엔
POSIX pty가 없어서 emulate_tty 효과가 제한적인 듯) **그래도 여전히
안 찍혔다**(사용자가 재확인) - 그래서 사용자 제안대로 접근을
아예 바꿨다: 투척 트리거를 토픽(`std_msgs/Empty`)에서 **서비스**
(`std_srvs/Trigger`)로 바꾸고, 응답(`success`/`message`)에 질량/
속도/설명을 담았다. 서비스 호출은 요청-응답이 호출한 프로세스
안에서 바로 왕복하므로, launch가 띄운 별도 프로세스의 출력 버퍼링
문제 자체와 완전히 무관해진다 - `ros2 service call`을 실행한 바로
그 터미널에 응답이 항상 찍힌다. (emulate_tty/PYTHONUNBUFFERED는
혹시 몰라 남겨뒀다 - 해는 없음.)

**설계 메모 - "누가 던질 공을 결정하는가"(나중에 바꿀 수도 있음)**:
지금은 `quad_mujoco_walk_ball` 노드(공을 실제로 던지는 쪽)가 질량/
속도를 **스스로** 결정한다(내부 `THROW_PRESETS`를 순서대로) - 호출자
(`ros2 service call`)는 "던져"라는 신호만 보내고 어떤 공인지는
모른다. 그래서 파라미터 없는 `std_srvs/Trigger`로 충분했다.

**반대로 호출자(또는 별도의 "던지는 주체" 노드)가 결정하게 하려면**
이야기가 달라진다 - `Trigger`로는 안 되고 질량/속도 값을 실어 보낼
메시지가 필요하다:
- 가장 간단히: 토픽(`std_msgs/Float32MultiArray`)으로 `[mass, speed]`
  발행.
- 더 깔끔하게: `mass`/`speed` 필드가 있는 커스텀 서비스 `.srv`를
  새로 정의(별도 `_interfaces` 패키지 필요 - 더 번거로움).

이러면 `quad_mujoco_walk_ball`은 "결정자"가 아니라 "실행자"가 되고,
`THROW_PRESETS`/순환 인덱스 로직은 호출자 쪽(또는 그 역할을 하는
새 노드)으로 옮겨가야 한다. 장점은 원하는 세기를 정확히 골라
던질 수 있다는 것, 단점은 지금처럼 반복 호출만으로 약→강 시나리오가
자동으로 펼쳐지는 편리함이 없어지고 그 시퀀스를 호출자가 직접
짜야 한다는 것 - 지금은 이 트레이드오프상 현재 구조(노드가 결정)를
그대로 유지하기로 함.

### 키보드로 cmd_vel 조작 (`teleop_keyboard`)

공식 `teleop_twist_keyboard` 패키지는 이 Windows ROS2 Humble
설치엔 안 깔려 있다(`ros2 pkg list`로 확인 - apt 바이너리가 없어서
git 클론+colcon build가 필요함). 그 대신 `view_quad_walk.py` 등과
조작 체계를 통일한 작은 노드를 직접 만들었다 - Windows 전용
`msvcrt`로 키 입력을 읽는다(이 프로젝트 ROS2 설치 자체가 Windows
전용이라 문제없음).

```
ros2 run humanoid_sim teleop_keyboard
```
Up/Down: 전진/후진 속도 증가/감소, Left/Right: 좌/우 회전 증가/감소,
Enter: 정지, Ctrl+C: 종료. 기본 발행 토픽은 `/quadruped/cmd_vel`
(`-p topic:=...`로 바꿀 수 있음). cmd_vel 타임아웃(1초) 안에 안
들어오면 로봇이 멈추는 안전장치가 있어서, 키를 안 눌러도 현재
속도를 10Hz로 계속 재발행한다.

## 휴머노이드 실제 관절 물리 보행 시도 (`humanoid_physics_walk.launch.py`) - 넘어짐

4족 로봇에 적용했던 "순수 애니메이션(`humanoid_state_publisher.py`)
대신 실제 관절 액추에이터로 걷기" 작업을 휴머노이드(2족)에도
그대로 적용해봤다 - 사용자가 "4족과 똑같이 시도 먼저, 결과는
그대로 공유"하기로 결정.

**정직한 결과: 넘어진다.** 4족은 다리 4개가 항상 땅에 닿아있어
정역학적으로 안정적이었지만, 2족은 좌우로 무게를 옮기는 메커니즘
(엉덩이 요/벌림 축이나 몸통 기울임)이 전혀 없어서, 한쪽 다리가
땅에서 떨어지는 순간 무게중심이 지지 발 바깥쪽에 있게 되어
구조적으로 쓰러진다.

**검증(ROS 없이, 독립 MuJoCo 스크립트)**: 4족의 걸음걸이 공식
(엉덩이 `amp*sin(phase)`, 무릎 `knee_amp*max(0,-cos(phase))`, 좌우
다리 반대 위상)을 그대로 2족용으로 다시 써서 주파수(0.5~2.0Hz) x
엉덩이 진폭(10~30도) 조합을 쓸어봤다:
- 기준선(진폭 0, 가만히 서있기): **완벽하게 안정적** - 문제가
  MJCF 자체에 있는 게 아님을 확인.
- 테스트한 모든 조합(주파수 5개 x 진폭 3개 = 15가지): **전부
  1.15~2.54초 안에 넘어짐**(롤 또는 피치가 85~178도까지 치솟아
  완전히 쓰러짐).
- 무릎을 전혀 안 굽혀도(발을 안 들어도) 엉덩이만 흔들면 3.2초에
  넘어지는 것도 확인 - 발을 드는 것만이 원인이 아니라, 체중이
  한쪽으로 쏠리는 순간 자체가 치명적이다.

좌우 밸런스 보강(엉덩이에 ab/duction 축 추가, 몸통 기울임 등)은
이번 작업의 범위 밖으로 다음 단계로 미뤘다 - 지금은 "진짜 관절
물리가 걷기를 시도하다가 넘어지는 모습" 자체를 정직하게 보여주는
데모로 완성했다.

**구현**: 4족의 무릎 추가 작업과 완전히 같은 패턴으로
`gen_humanoid_assets.c`에 `THIGH_LEN`/`SHIN_LEN`(각 0.6, 기존
`LEG_LEN`=1.2를 반으로) 분리 + 무릎 관절(`LeftLeg_to_LeftShin`/
`RightLeg_to_RightShin`, 0~90도)을 추가했다 - `humanoid_test.c`/
`humanoid_loader_test.c`(OpenGL 데모)도 같이 업데이트해서 일관성을
유지했다(재컴파일해서 직접 띄워 크래시 없음을 확인). ROS2 쪽은
`ros2_ws/src/humanoid_sim/mujoco/humanoid_walk.xml`(quad_walk.xml과
같은 패턴 - body box `size="0.25 0.4 0.7"`, head sphere, 다리 2개
각각 허벅지+종아리 캡슐 2세그먼트 + 액추에이터 4개) +
`humanoid_mujoco_walk.py`(quad_mujoco_walk.py와 같은 구조, 다만
**cmd_vel은 없음** - 기본 보행 시도 자체가 되는지가 먼저 확인할
것이라 4족도 처음엔 고정 보행만 만들고 cmd_vel은 나중에 따로
추가했던 순서를 그대로 따름). 넘어지기까지 약 1.8초짜리 조합
(freq=0.85Hz, 엉덩이 진폭 20도, 무릎 진폭 15도)을 그대로 썼다 -
어차피 넘어지므로 정교한 튜닝은 의미가 없다.

실행:
```
ros2 launch humanoid_sim humanoid_physics_walk.launch.py
```

**버그 수정 (2026-11-17): 팔이 안 보이던 문제.** 처음 실행했을 때
사용자가 "팔이 없이 넘어져 있다"고 보고 - 4족 무릎 때 겪은 것과
같은 버그 패턴이었다. `humanoid_mujoco_walk.py`의 `JOINT_NAMES`가
다리/무릎 관절만 담고 있어서 `body_to_leftarm`/`body_to_rightarm`
관절값이 한 번도 발행되지 않았고, `robot_state_publisher`는 값을
못 받은 관절 아래 링크(팔)의 TF를 계산하지 못해 전혀 렌더링하지
않았다. 팔은 이 데모의 물리(다리 보행)와 무관해서 MJCF에는 아예
안 넣었지만, URDF에는 관절이 있으므로 **물리와 무관하게 고정값
(0.0, 옆으로 늘어뜨린 자세)으로라도 발행**해야 보인다 - `ARM_JOINT_NAMES
= ("body_to_leftarm", "body_to_rightarm")`를 추가해서 매 틱
`JointState`에 `0.0` 두 개를 같이 발행하도록 고쳤다. 같은 보고에서
"센터에 하얀 사각 기둥"도 언급됐는데, 재확인해보니 별도 버그가
아니라 **몸통(torso) 메쉬 자체**였다 - `body_ros.obj`/`.mtl`은
처음부터 정상이었고(0.5×0.8×1.4 박스, `Kd 0.55 0.55 0.65`), 팔이
안 보여서 몸통만 덩그러니 서 있는 모습이 "사각 기둥"처럼 보였던
것. 팔 수정 후 재확인 결과 둘 다 해결됨(사용자 확인: "팔보이고
흰기둥 없어졌어").

## 좌우/전후 밸런스 메커니즘 추가 + LQR로 "서있기" 안정화 (2026-11-17)

위 섹션의 "넘어짐"은 좌우 밸런스 메커니즘이 전혀 없어서였다 -
사용자가 "두 발 달린 짐승의 비애"라며 이 작업을 시작하자고 요청,
"가만히 서서 균형 잡는 것부터 해보자"는 방향으로 좁혀서 진행했다.
전부 ROS 없이 독립 스크립트(세션 스크래치 디렉터리의
`humanoid_stand_lqr.py` 등)로 먼저 검증한 뒤 반영했다.

**1단계 - 엉덩이 ab/duction(좌우) 축만 추가**: 오픈루프 흔들림과
PD 피드백을 둘 다 시도했지만 생존 시간이 1.57초 -> 최선 2.4초
정도로만 개선됐다. 넘어지는 방향을 조사해보니(기존 roll/pitch
Euler 분해는 큰 회전에서 짐벌락 아티팩트가 섞여 믿을 수 없었음 -
토르소 로컬 Z축이 월드 수직과 이루는 각도로 다시 측정) 상당수가
**앞/뒤(피치) 방향**으로 쓰러졌다 - ab/duction(좌우 축)이 구조적
으로 전혀 손댈 수 없는 실패 모드. 다리 끝이 둥근 캡슐 "점 접촉"
이라 한발 지지 때 지지 다각형이 사실상 점이었던 게 원인이었다.

**2단계 - 발목(롤+피치) + 평평한 발 추가**: 지지 다각형이 생겨서
패시브(제어 없음)로도 조금 나아졌지만(1.79초), 발목 PD만으로는
복원력이 구조적으로 너무 약함(5도 명령에 1초 뒤 0.09도 반응 -
엉덩이의 28분의 1). 사용자 제안대로 엉덩이+발목+무릎을 다 동원한
그리드서치, 이어서 **허리(롤+피치) 관절까지 새로 추가**(상체를
하체와 분리해서 독립적으로 움직이는 "다이빙 선수" 전략)하고
**랜덤서치(최대 1000개 게인 조합, 15차원)**까지 돌려봤지만 전부
6초 안에 실패 - 단순 PD(그리드/랜덤서치 포함)로는 한계였다는 걸
충분히 확인했다. (무릎은 0~90도 한쪽으로만 굽혀져서 양방향 보정이
구조적으로 불가능하다는 것도 확인 - `base`를 바꿔도 결과가 거의
안 변하고 `kp`/`kd`만 바꿔선 의미 있는 차이가 없었음.)

**LQR(Linear-Quadratic Regulator) 기본 원리 (사용자 요청으로 기록)**:
1. **선형화** - 평형점(가만히 서있는 자세) 근처에서는 복잡한 비선형
   물리도 근사적으로 `오차(다음) ≈ A·오차(지금) + B·제어(지금)`라는
   선형 관계로 볼 수 있다. 여기서 "오차"는 관절 각도/속도가 평형
   에서 얼마나 벗어났는지, "제어"는 액추에이터에 주는 보정값이다.
   A, B는 `mujoco.mjd_transitionFD`가 수치 미분으로 직접 계산해줘서
   손으로 유도할 필요가 없다(부호/커플링을 손으로 추측하다 여러
   번 틀렸던 문제가 여기서 해결됨).
2. **비용함수** - "자세가 많이 틀어지는 것"(Q 행렬로 가중치)과
   "힘을 너무 세게 쓰는 것"(R 행렬로 가중치) 둘 다 나쁘다고 점수를
   매긴다: `비용 = Σ (오차^T Q 오차 + 제어^T R 제어)`.
3. **Riccati 방정식** - 이 비용을 가장 작게 만드는 제어 법칙이
   수학적으로 단 하나의 형태 `제어 = -K·오차`(K는 고정 행렬)로
   나온다는 게 LQR 이론의 핵심 결과 - K는 Riccati 방정식을 풀어야
   구해진다(scipy 없이 `solve_dare()`로 numpy 반복법 직접 구현).
4. **왜 PD보다 나은가** - 손으로 짠 PD는 관절 하나하나를 따로 보고
   부호/게인을 추측했다. LQR의 K는 "이 관절을 움직이면 다른 관절
   쪽 균형에 어떤 영향을 주는지"까지 한 번에 고려해서 계산되므로,
   모든 관절이 서로 도와가며 균형을 잡는다.
5. **한계** - 평형점 "근처"에서만 성립하는 근사라서, 평형에서 많이
   벗어나면(예: 외력으로 크게 밀었을 때) 선형 근사가 깨져서 못
   버틴다 - `view_humanoid_stand.py`의 화살표 키 밀기 테스트로 확인
   (아래 "다음 단계(아직 안 함)" 참고 - Q/R 재조정 또는 더 큰
   교란까지 버티는 설계 필요).

**3단계 - LQR**: 사용자가 "LQR 구현하기 어렵니?"라고 물어서, 생각보다
안 어렵다고 답했다 - `mujoco.mjd_transitionFD`가 평형점 주변의
선형화(A, B 행렬)를 수치 미분으로 자동 계산해줘서, 지금까지 손으로
추측하다 여러 번 틀렸던 부호/관절 간 커플링을 전부 자동으로 올바르게
잡아준다. scipy가 안 깔려 있어서(`solve_discrete_are` 없음)
discrete-time Riccati 방정식은 numpy 반복법으로 직접 풀었다
(`solve_dare()` - `P = Q + A^T P A - A^T P B (R+B^T P B)^-1 B^T P A`를
수렴까지 반복). 결과: **300초(5분) 완전 안정, 최대 기울기 0.06도** -
모든 PD 시도 중 최선(~5.8초) 대비 50배 이상 개선.

튜닝 중 교훈 하나: 가슴(Chest) 메쉬의 오프셋이 겹쳐 있던 버그를
고치고 나니(시각적으로는 고쳐야 맞는 것이었지만) 같은 게인으로
118초 -> 6.45초로 나빠졌다 - 질량 분포가 조금만 바뀌어도 선형화
기준점이 달라져서 게인을 다시 찾아야 했다(재탐색 후 300초로 복구).
**LQR도 한 번 잘 됐다고 영원히 되는 게 아니라, 모델이 바뀌면
다시 풀어야 한다** - 그래서 게인을 파일에 박아넣지 않고 노드가
시작할 때마다 직접 선형화+Riccati를 푼다(`HumanoidMujocoWalk.__init__`
의 `find_equilibrium`/`linearize`/`solve_dare` 호출, 수백 ms 이내).

**구현**: `humanoid_walk.xml`에 엉덩이 ab/duction, 발목(롤+피치),
허리(롤+피치) 힌지 + 평평한 발 geom + 액추에이터 8개를 추가(총
12개 액추에이터). `gen_humanoid_assets.c`도 같은 구조를 URDF에
반영 - `Body`(골반, 기존 `body_ros.obj`를 반으로 쪼갠 `pelvis_ros.obj`)
위에 `ChestRoll`(visual 없음, `base_link`와 같은 연결용 링크 패턴)
+ `Chest`(`chest_ros.obj`, 머리/팔이 이제 여기 붙음), 다리 쪽은
`LeftHip`/`RightHip`(visual 없음, ab/duction) + 기존 `LeftLeg`~
`LeftShin` 다음에 `LeftAnkleRoll`(visual 없음) + `LeftFoot`
(`foot_ros.obj`, 새 지지 다각형) 추가. **OpenGL 데모
(`humanoid_test.c`/`humanoid_loader_test.c`)는 이번에도 손대지
않았다** - 밸런스는 순수 물리 개념이라 애니메이션 데모엔 의미가
없고, 씬 파일 포맷이 다중 관절 노드를 지원하지 않아서 비용 대비
이득이 낮다고 판단(이전 ab/duction-only 결정과 같은 이유).

`humanoid_mujoco_walk.py`는 `compute_leg_targets()` 같은 오픈루프
공식을 전부 버리고, 매 틱 `-K @ (현재상태 - 평형상태)`로 제어한다
(`mujoco.mj_differentiatePos`로 자유관절 쿼터니언을 포함한 상태
오차를 접공간에서 올바르게 계산). **cmd_vel/전진 보행은 아직 없음
- 이번엔 "서있기" 자체의 안정화까지만이고, 걷기는 다음 단계.**

실행:
```
ros2 launch humanoid_sim humanoid_physics_walk.launch.py
```

**RViz2 디버깅 중 발견 - 발이 땅보다 살짝 떠 보임(2026-11-17).**
접촉력/순방향기구학을 전부 검산해도 "발이 거의 정확히 z≈0에 닿는다"
는 결과만 나와서, ROS/URDF/RViz2 파이프라인을 다 건너뛰고 MuJoCo
자체 뷰어로 직접 확인하는 `mujoco/view_humanoid_stand.py`를 만들었다
(ROS2/DDS와 전혀 무관, `humanoid_mujoco_walk.py`와 같은 LQR 로직을
그대로 복제 - 공유 모듈로 뽑기엔 과해서 `view_quad_walk.py`와 같은
이유로 중복 유지, 둘 중 하나 고치면 반드시 둘 다 고칠 것). 결과:
MuJoCo 자체 렌더링에서는 발이 그림자까지 포함해서 정확히 땅에
닿아있었다 - RViz2 쪽 각도/렌더링 문제였을 가능성이 높다.

이 직접 렌더링 과정에서 발견한 **진짜 버그 2개**를 추가로 고쳤다:
1. **종아리 캡슐 끝이 발목 피벗보다 더 아래로 튀어나와 있던 문제**
   (캡슐은 `fromto` 선분 양 끝에 자기 반지름만큼 둥글게 더 튀어나옴 -
   `fromto`를 `SHIN_LEN - 반지름(0.07)`로 줄여서 고침). 이것 때문에
   실제로는 종아리 끝이 먼저 땅에 닿고 그 반작용으로 발 전체가
   ~7cm 떠 있었다 - 즉 **이전까지는 발목을 제어해도 발이 땅에
   안 닿아서 실제로는 아무 효과가 없었다**(엉덩이+무릎+허리만으로
   버티던 것 - 발목 on/off 비교 실험으로 확인: 평형 유지 시 발목
   켜면 60초 완전 안정(최대 기울기 0.005도), 끄면 5.63초 만에
   넘어짐 - 수정 후에는 진짜로 발목이 일하고 있다는 뜻).
2. **머리가 가슴 상자에 절반쯤 파묻혀 있던 문제**(MuJoCo로 직접
   렌더링해보고서야 눈에 띔) - 처음엔 `body_to_head_z`를
   `BODY_H/2 + HEAD_R`로 고쳤는데, 이건 **MJCF(MuJoCo 기본 sphere,
   중심 기준 pos)에만 맞는 수정이었다.** URDF의 `head_ros.obj`는
   `write_sphere_obj_zup`의 `center_z=HEAD_R` 인자로 이미 "바닥이
   원점" 오프셋이 구워져 있어서(leg_ros.obj 등과 같은 관례),
   여기에 또 `HEAD_R`을 더하면 오프셋이 중복돼서 머리가 가슴에서
   `HEAD_R`(0.35m)만큼 떠버렸다(사용자가 RViz 스크린샷으로 발견
   - "코드/물리는 다 맞는다"고 결론 내렸다가 "머리 떠 있잖아"라는
   사용자 지적에 재검토해서 찾음). **URDF 쪽만** `BODY_H/2`로 되돌려
   바로잡았다 - MJCF의 `BODY_H/2 + HEAD_R`는 그대로 유지(두 파일이
   서로 다른 관례를 쓴다는 걸 혼동하지 말 것).

**팔도 물리에 추가(2026-11-17)** - 사용자 제안("팔이 움직이면
무게중심이 바뀌잖아"): 어깨(가슴 원점, `arm_z=BODY_H/2`,
`SHOULDER_X=BODY_W/2+ARM_W/2`)에서 매달린 1축(피치) 캡슐 팔 2개를
`humanoid_walk.xml`에 추가(URDF의 기존 `body_to_leftarm`/
`rightarm` 관절 이름을 그대로 재사용 - 전엔 고정 0만 받다가 이제
실제 LQR 제어값을 받는 것만 다름). `nu`가 12→14, `nv`가 18→20으로
늘었지만 같은 비용함수 가중치로 300초 안정 재검증 통과(재조정
불필요). 외력(화살표 키로 push, 뒤에 추가) 테스트에서 팔이 실제로
크게(최대 38.6도) 흔들리며 생존 시간을 늘려주는 것도 확인(중간
세기 충격에서 ~15% 개선, 큰 충격에서는 차이 없음 - 사람이 휘청일
때 팔을 휘젓는 것과 같은 효과).

**모양 통일 작업(2026-11-17, 사용자 요청들)**: MJCF는 다리/팔이
capsule인데 URDF는 box라 안 맞아서, URDF 쪽 다리/팔 메쉬를
`write_cylinder_obj_zup()`(새로 작성)로 원기둥화. 이어서 "가슴과
원통도 타원형이면 이쁠 것"이라는 요청으로 `write_elliptic_cylinder_obj_zup()`
로 일반화해서 가슴/골반까지 타원 단면 원기둥으로. 그런데 MuJoCo는
타원 단면 원기둥이 없어서 MJCF 쪽 몸통은 원형 `cylinder`(반지름
0.32)로 타협 - 그 다음 "통일성을 위해 RViz 쪽도 원형으로" 요청으로
URDF 몸통도 같은 반지름(`TORSO_RADIUS=0.32`)의 원형으로 재통일.
이 과정에서 몸통 반지름이 박스 시절(0.4) 대비 작아지면서 팔
부착 위치가 몸통에서 떨어져 보이는 부작용이 두 번(MJCF, URDF) 났고,
둘 다 "원기둥 반지름 + 팔 반지름"으로 어깨 오프셋을 다시 계산해서
고쳤다(URDF 쪽은 OpenGL 데모가 공유하던 기존 `SHOULDER_X` 상수를
안 건드리려고 `URDF_SHOULDER_X`를 새로 분리). 빨간 코도
MJCF(`nose_geom`)에 추가했다가 "이마에 붙었다"는 지적으로 머리
중심 높이로 재조정(URDF `nose_z`도 같이 수정, MJCF/URDF 둘 다
처음엔 `HEAD_R`만큼 위였다가 `0`으로).

**숨어있던 진짜 버그 - 제어 주기(2026-11-17)**: 위 작업들을 다
반영하고 재부팅까지 했는데도 RViz2에서만 "3초 만에 쓰러짐 + 머리가
또 떠 보임" 증상이 재현됐다. 독립 검증 스크립트는 전부 매 물리
스텝(0.005s)마다 LQR 제어를 다시 계산했는데, 실제 노드
(`on_timer()`)는 **0.01초(`TIMER_PERIOD_SEC`)에 한 번만 계산하고
`PHYSICS_SUBSTEPS`(2)번의 물리 스텝 동안 그 값을 그대로 유지**하고
있었다 - 즉 실질 제어 주기가 절반으로 느려져 있었다. 이 차이
하나만 재현해봐도 2.81초에 넘어짐 - K는 매 스텝 재계산을 전제로
풀린 게인이라 절반 속도로는 불안정했던 것. `on_timer()`가 각
substep마다 상태를 다시 읽고 제어를 다시 계산하도록 고쳐서
해결(300초 재검증 통과). "머리 떠 보임"은 이 불안정 때문에 로봇이
실제로 넘어지는 과정에서 생긴 현상이었고, 별도의 기하학 버그는
아니었다(위의 URDF `body_to_head_z` 버그와는 다른 사건 - 그건
그것대로 진짜 버그였고 이미 고쳤음).

## 중요 - Claude가 직접 노드를 띄워 테스트하는 것의 위험성

이 세션에서 디버깅용으로 `ros2 run`/`ros2 launch`를 수십 번
직접 실행하고 강제종료(Force-Kill)하면서, **이 Windows 머신의
ROS2 CLI 데몬 / Fast-DDS 공유메모리 디스커버리 상태가 두 번이나
망가졌다** - 증상은 실제 노드가 멀쩍하게 잘 돌고 있어도 RViz2가
"Fixed Frame: world does not exist"만 띄우거나, `ros2 node list`/
`ros2 topic info` 같은 기본 CLI 명령조차 멈춰버리는 것이었다.
스크립트로는 못 고쳤고, **재부팅이 유일하게 확인된 해결책**이었다.

그래서 이후로는: Claude가 테스트를 위해 직접 `ros2 run`/`launch`로
노드를 띄우는 걸 최소화하고, 코드 리뷰/정적 검증(문법 검사, MJCF
유효성, 수치 계산 직접 검증) 위주로 하고, 실제 RViz2 확인은 사용자가
직접 하는 쪽으로 방향을 바꿨다. `ros2 run` 같은 명령이 **wrapper
프로세스를 띄우고 실제 실행 파일은 그 자식 프로세스**라서, wrapper
PID만 죽이면 실제 노드는 안 죽고 좀비로 남는 것도 이번에 알게 된
함정이다(`Get-CimInstance Win32_Process`로 실제 자식 PID를 찾아야
한다).

**업데이트 (다음 세션): 읽기 전용 구독조차 위험하다고 확인됐다.**
사용자 세션이 돌고 있는 동안, Claude가 `/tf`를 구독만 하는(아무것도
발행 안 하는) 스크립트를 딱 하나 띄웠는데, 그 자체가 사용자의 이미
멀쩍하게 돌고 있던 RViz2의 TF를 깨버렸다. 즉 "노드를 띄웠다 죽이는
것"만이 아니라, **이 환경에서는 어떤 새 DDS 참가자가 끼어드는 것
자체가 위험하다** - 읽기 전용이어도, 금방 끝나도 마찬가지다.

**그래서 찾은 안전한 대안: `ros2 bag record`를 Claude가 아니라
사용자가 직접 띄우게 하고, 녹화 끝난 뒤 생긴 `.db3` 파일을 Claude가
오프라인으로(네트워크/DDS 전혀 없이) 분석한다.** `rclpy.serialization.
deserialize_message()`로 CDR 직렬화를 풀면 되는데, 이건 순수 로컬
CPU 연산이라 `rclpy.init()`도, 노드 생성도, 네트워크 소켓도 전혀
필요 없다 - `sqlite3`로 `.db3`를 열어서 `/tf` 토픽의 raw 메시지를
읽고, `tf2_msgs.msg.TFMessage`로 역직렬화해서 원하는 `child_frame_id`
만 뽑아 시계열로 분석하면 된다(`C:\Python38\python.exe`에 이미
`rclpy`/`tf2_msgs`가 있으므로, ROS2 환경만 `call local_setup.bat`로
sourcing해서 import 경로만 맞추면 됨 - 노드를 안 띄우니 안전하다).
이 방법으로 실제로 위치/회전/각속도 이상(위 "아직 안 풀린 문제"
섹션)을 직접 찾아냈다 - 화면 녹화/스크린샷보다 훨씬 정확하고,
사용자에게 아무 추가 작업도 안 시켜도 된다(녹화는 어차피 사용자가
직접 트리거해야 하지만).

## 원본 OpenGL 데모와 다른 점 (의도적으로 생략한 것)

- 키보드로 주인공을 수동 조작/정지시키는 기능(`MAIN_MODE_MANUAL`/
  `MAIN_MODE_STOPPED`)은 포팅하지 않았다 - 주인공이 늘 경로를 자동
  으로 걷는 것만 재현한다 (RViz는 보기용이라 키보드 조작까지
  옮기는 건 범위 밖으로 뒀다).
- 여러 캐릭터(클론)와 옷 색 틴트, 땅/하늘/그림자/나무 같은 배경
  소품은 로봇 모델이 아니라서 아예 포함하지 않았다. 자세한 내용은
  `computer_graphics/humanoid_extra.yaml` / `quadruped_extra.yaml`
  참고.
- `t`(애니메이션 시간)는 두 노드가 각자 독립적으로 흘린다 - 원본
  C 코드는 humanoid와 4족 로봇이 같은 `idle()`의 `t`를 공유했지만,
  두 로봇의 위상이 서로 맞든 안 맞든 기능적으로 의미가 없어서
  단순하게 분리했다.
